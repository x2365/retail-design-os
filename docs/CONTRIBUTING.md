# CONTRIBUTING — правила командной работы над RetailDesign OS

**Дата:** 2026-06-05 · Язык общения: русский · Главная сущность системы — **Task**.

Цель этого документа — чтобы при любых изменениях и дополнениях система **не
сыпалась**, а структура оставалась пригодной для развития продукта. Это рабочее
соглашение обязательно к соблюдению (и человеком, и AI-ассистентом).

---

## 0. Источники истины (иерархия)

При конфликте — приоритет сверху вниз:

1. **`BUSINESS_RULES.md`** — бизнес-правила: жизненный цикл Task (12 этапов),
   правила переходов, ограничения сущностей, финансы.
2. **`docs/DATABASE.md`** — актуальная схема БД (таблицы, связи, индексы, enum).
3. **`AI_CONTEXT.md`** — режимы работы и критические правила кода.
4. **`docs/MIGRATIONS.md`** — как версионируется схема.
5. Код (`models → schemas → services → routers`).

Правило: **никакая важная логика не живёт «в голове» или только в комментариях** —
только в этих документах + в коде (Enums, validators, services). Меняешь поведение —
обнови соответствующий документ в той же задаче.

---

## 1. Архитектурные инварианты (ломать нельзя)

Эти правила нарушать запрещено; нарушение = задача отклоняется.

1. **Деньги — только `Integer` в копейках.** Валюта — отдельным полем `currency`.
   Канонический показатель стоимости задачи — `tasks.production_cost`;
   `budget/sample_cost/tirazh_cost/prepaid` — детализация. Конвертация
   копейки↔рубли на фронте — **только в адаптерах приёма данных** (одна точка).
2. **Даты/время — `datetime` в UTC.** (Незакрытый техдолг: `deadline_tt/launch_date/
   kp_date` ещё `Date` — переводятся на шаге №4.)
3. **Этапы — только через `TaskStage` (IntEnum 1..12).** Никаких «голых» int/строк
   в новом коде. Переходы — только через `services/task_stage.py`
   (вперёд +1, возврат назад, без исключений; этап 12 — по предусловиям).
4. **Не создавай новые сущности, если можно расширить существующие.**
5. **Не храни растущую бизнес-логику в JSON** (approvals, история, версии → таблицы).
   Временные JSON (`tasks.stage_approvals`) помечены к миграции на таблицу.
6. **Не меняй существующие связи** (`ForeignKey`, `back_populates`, кардинальность)
   **без явного согласования.** Изменение связи = отдельное согласованное решение.
7. **Ограничения целостности — на уровне БД, а не только в API:** `UNIQUE`,
   `CHECK`, `FK ON DELETE`. Примеры действующих: `payments.task_id UNIQUE` (1:1),
   `deliveries (task_id, retail_point_id) UNIQUE`, `tasks.stage CHECK 1..12`,
   `documents` CHECK «есть владелец (task_id или equipment_id)».

## 2. Структура и слои

```
app/
  models/              # SQLAlchemy 2.0 модели (пакет): base, enums,
                       #   reference, library, task, ops; __init__ ре-экспортирует
  schemas.py           # Pydantic v2 (вход/выход API)
  serializers.py       # ORM → схемы выдачи
  aggregates.py        # вычисляемые значения (НЕ хранятся: счётчики ТТ, KPI)
  services/            # бизнес-логика (task_stage, library, ...)
  routers/             # HTTP-эндпоинты (тонкие: валидация + вызов services)
  security.py          # auth/JWT/RBAC
migrations/            # Alembic
docs/                  # DATABASE.md, MIGRATIONS.md, этот файл
```

Правила:
- **Роутеры тонкие.** Нетривиальная логика (переходы этапов, создание связанных
  сущностей, гейтинг) — в `services/`, не в роутере.
- **Вычисляемые значения не хранятся** (дни до дедлайна, прогресс, счётчики ТТ,
  KPI) — считаются агрегатами в `aggregates.py`.
- Современный SQLAlchemy 2.0 (`select`, `selectinload`/`joinedload`), Pydantic v2.

## 3. Процесс внесения изменений

1. **Указывай режим** (по `AI_CONTEXT.md`): Архитектор (анализ) / Разработчик
   (код) / Ревьюер (проверка).
2. **Атомарные шаги.** Одна задача = одно понятное изменение. Большие фичи
   разбиваются на последовательность атомарных шагов с ревью после каждого.
3. **Объявляй область правок:** какие файлы трогаем и какие — **нет**.
4. **Сначала архитектура спорных мест.** Если изменение затрагивает инвариант
   (раздел 1) или связь — сперва согласование, потом код.
5. **Не ломай обратную совместимость API без необходимости.** Добавляешь поле —
   делай его опциональным со значением по умолчанию.

---

## 4. Миграции (обязательно)

- Любое изменение модели → **отдельная Alembic-ревизия** поверх предыдущей
  (`down_revision` указывает на текущий head). Имена: `000N_краткое_описание.py`.
- **Никогда не редактируй уже применённую миграцию** — добавляй новую.
- Для SQLite — `render_as_batch=True` (уже в `env.py`) для `ALTER`.
- Проверяй, что цепочка `alembic upgrade head` применяется на чистой БД и что
  `create_all` (дев) даёт ту же схему.
- Меняешь типы/семантику данных (напр. рубли→копейки) — пиши **data-миграцию**
  (`op.execute(UPDATE ...)`) и `downgrade`.
- Подробности — `docs/MIGRATIONS.md`.

---

## 5. Тесты (без зелёных тестов задача не закрыта)

- Каждое изменение сопровождается тестами: **загрузка / изменение / валидация**.
- `test_smoke.py` должен оставаться **зелёным**; правило поменялось — обнови тест
  под новое правило (не удаляй проверку).
- Минимальный набор для новой фичи: happy-path, валидация (некорректные данные →
  4xx), RBAC (viewer → 403), целостность (нарушение CHECK/UNIQUE → ошибка).
- Прогоняй тесты **до** упаковки архива.

---

## 6. Безопасность (поддерживать всегда)

- Все `/api/*` (кроме `/auth/login`, `/health`) — под токеном. Запись — по ролям
  (`require_roles`), viewer не пишет.
- Загрузка файлов: белый список расширений, очистка имени, лимит размера, запрет
  пустых; скачивание — защита от path traversal. Те же проверки — для любых новых
  точек загрузки (общий хелпер `_validate_and_store`).
- Никаких секретов в коде; в проде — `JWT_SECRET` обязателен (fail-fast),
  Swagger скрыт, CORS без credentials, security-заголовки.
- Валидация на входе: суммы `ge=0`, `stage 1..12`, типы из enum/белых списков,
  длины строк.

---

## 7. Фронтенд

- **Не переписывать render-логику без необходимости.** Данные приходят из API
  через адаптеры (`adaptTask`, `adaptGroup`) — там же единственная конвертация
  денег (копейки→рубли).
- Подписи этапов берём из бэкенда (`/dashboard/meta`); не хардкодить полный
  список в JS (короткие подписи вкладок — единый массив `STAGE_TAB_LABELS`).
- После правок JS — обязательная проверка синтаксиса: `node --check` извлечённого
  скрипта. Не оставлять незакрытые шаблоны/кавычки.
- Никакого `localStorage`/`sessionStorage` в артефактах; состояние — в памяти/через API.

---

## 8. Запуск и деплой (чтобы «не сыпалось» локально)

Жёсткие уроки эксплуатации:

1. **Нужны два сервера одновременно:** бэкенд `:8000` (uvicorn) и фронтенд `:5500`
   (`python -m http.server`). Падает любой — на фронте «Failed to fetch».
2. `http.server` отдаёт **папку, из которой запущен** — проверяй, что запускаешь
   из свежей папки. Истина о том, что реально отдаётся, — через
   `curl -s http://localhost:5500/ | grep -c "<маркер новой версии>"` (в обход кэша браузера).
3. Перед запуском новой версии **убей старые процессы**:
   `lsof -ti:8000 | xargs kill -9` и `lsof -ti:5500 | xargs kill -9`.
4. **Изменилась схема → удали `retaildesign.db`** (дев) или `alembic upgrade head`
   (прод). Иначе старая БД конфликтует с новыми колонками.
5. В браузере — жёсткое обновление `Cmd+Shift+R` (сброс кэша).
6. Проверяй версию по содержимому: `grep -rc "<маркер>"` в `app/models/`/`index.html`
   (например, `production_cost` / `productionCost`) — а не «по ощущению».

## 9. Definition of Done (чек-лист перед «готово»)

- [ ] Соблюдены инварианты (раздел 1); связи не менялись без согласования.
- [ ] Логика — в нужном слое (services, не роутер); вычисляемое не хранится.
- [ ] Есть Alembic-ревизия; цепы `upgrade head` и `create_all` дают одну схему.
- [ ] Добавлены тесты (load/change/validation/RBAC); `test_smoke.py` зелёный.
- [ ] Безопасность не ослаблена (auth, RBAC, валидация, загрузка файлов).
- [ ] Обновлён `DATABASE.md`/`BUSINESS_RULES.md`, если менялись схема/правила.
- [ ] Фронт: `node --check` проходит; деньги через адаптер; этапы из бэкенда.
- [ ] Указано, какие файлы менялись и что трогать **не** нужно.

---

## 10. Чего не делаем никогда

- Не храним деньги в рублях/строках/`float`; не считаем KPI мимо `production_cost`.
- Не используем «голые» числа для этапов; не двигаем этапы мимо `task_stage`.
- Не редактируем применённые миграции; не меняем схему «руками» в обход Alembic
  (в проде).
- Не меняем `ForeignKey`/кардинальность связей без явного согласования.
- Не упаковываем/не отдаём сборку с красными тестами.
- Не складываем растущую бизнес-логику в JSON-поля.
